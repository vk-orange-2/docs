

# ТЗ: Distributed Real-Time Configuration Delivery Platform

## 1. Функциональные требования

### 1.1. Управление конфигурациями

1. [ ] **FR-1.** Система должна позволять создавать конфигурацию.
2. [ ] **FR-2.** Система должна позволять получать конфигурацию по идентификатору.
3. [ ] **FR-3.** Система должна позволять обновлять конфигурацию.
4. [ ] **FR-4.** Система должна позволять удалять конфигурацию.
5. [ ] **FR-5.** Система должна поддерживать формат конфигурации key-value.
6. [ ] **FR-6.** Система должна поддерживать формат конфигурации JSON.
8. [ ] **FR-7.** Каждая конфигурация должна быть привязана к конкретному сервису.
9. [ ] **FR-8.** Каждая конфигурация должна быть привязана к конкретному окружению.
10. [ ] **FR-9.** Система должна поддерживать окружения dev, stage и prod.
11. [ ] **FR-10.** Система должна позволять получать список конфигураций по сервису.
12. [ ] **FR-11.** Система должна позволять получать список конфигураций по окружению.
13. [ ] **FR-12.** Система должна позволять получать список конфигураций по комбинации service + environment.
14. [ ] **FR-13.** Система должна валидировать корректность формата конфигурации перед сохранением.
15. [ ] **FR-14.** Система должна сохранять изменение конфигурации в PostgreSQL до начала доставки клиентам.

---

### 1.2. Версионирование

16. [ ] **FR-16.** Каждое изменение конфигурации должно создавать новую версию.
17. [ ] **FR-17.** Номер версии должен возрастать монотонно в рамках одной конфигурации.
18. [ ] **FR-18.** Каждая версия должна содержать timestamp изменения.
19. [ ] **FR-19.** Каждая версия должна содержать идентификатор автора изменения.
20. [ ] **FR-20.** Система должна хранить историю версий конфигурации не менее чем за последний год.
21. [ ] **FR-21.** История версий должна быть доступна для чтения через API.
22. [ ] **FR-22.** Система должна позволять получить конкретную версию конфигурации.
23. [ ] **FR-23.** Система должна позволять выполнить глобальный rollback конфигурации на выбранную предыдущую версию.
24. [ ] **FR-24.** Rollback (включая rollback, инициированный из rollback rollout) должен создавать новую версию, а не изменять существующую.
25. [ ] **FR-25.** Система должна позволять получить diff между двумя версиями конфигурации.

---

### 1.3. Доставка конфигурации

Centrifugo — это realtime messaging server с каналами pub/sub; основной клиентский транспорт у него WebSocket, а backend может публиковать сообщения через Server API. По документации модель доставки по умолчанию — **at-most-once**, а **at-least-once** достижима только при включенной history/recovery и в пределах окна хранения истории. Поэтому в ТЗ лучше явно зафиксировать архитектурные ограничения и не обещать абсолютную доставку вне recovery window. ([centrifugal.dev][1])

26. [ ] **FR-26.** Система должна поддерживать push-модель доставки конфигурации клиентам.
27. [ ] **FR-27.** Система не должна требовать polling как обязательный механизм доставки.
28. [ ] **FR-28.** Система должна использовать Centrifugo как компонент доставки конфигурационных обновлений клиентам.
29. [ ] **FR-29.** Система должна публиковать событие доставки в Centrifugo только после успешной записи новой версии конфигурации в PostgreSQL.
30. [ ] **FR-30.** Система должна выполнять доставку обновлений клиентам по WebSocket через Centrifugo.
31. [ ] **FR-31.** Клиент должен получать обновление автоматически после публикации новой версии конфигурации.
32. [ ] **FR-32.** Клиент должен получать номер версии вместе с доставляемой конфигурацией.
33. [ ] **FR-33.** Система должна обеспечивать порядок доставки обновлений в рамках одной конфигурации.
34. [ ] **FR-34.** При каждом подключении или восстановлении соединения клиентский агент должен инициировать version reconciliation через HTTPS API: POST /v1/configs/{configId}/reconcile.
35. [ ] **FR-35.** В ответ на reconciliation сервер должен возвращать действие action: none | recovery | snapshot и актуальную серверную версию конфигурации.
36. [ ] **FR-36.** Восстановление пропущенных сообщений через Centrifugo recovery должно выполняться только в пределах окна history/recovery; если окно превышено или recovery недоступен, сервер должен вернуть action=snapshot, а агент должен загрузить актуальную конфигурацию через GET /v1/configs/{configId}. ([centrifugal.dev][2])

### 1.4. Управление секретами

39. [ ] **FR-39.** Система должна поддерживать признак секретности конфигурации (is_secret) с отдельными политиками доступа, хранения и маскирования.
40. [ ] **FR-40.** Секреты должны храниться в зашифрованном виде.
41. [ ] **FR-41.** Секреты должны передаваться клиентам только по защищенному каналу.
42. [ ] **FR-42.** Система должна ограничивать доступ к секретам по ролям или ACL.
43. [ ] **FR-43.** Система должна маскировать секреты при чтении через UI.
44. [ ] **FR-44.** Система должна маскировать секреты при чтении через API, если у вызывающего нет прав на полный просмотр.
45. [ ] **FR-45.** Система должна фиксировать каждое изменение секрета в журнале аудита.
46. [ ] **FR-46.** Система должна хранить историю версий секрета в соответствии с требованиями к версионированию.

---

### 1.5. Rollout-стратегии

47. [ ] **FR-47.** Система должна поддерживать мгновенное обновление конфигурации для всех целевых клиентов.
48. [ ] **FR-48.** Система должна поддерживать gradual rollout по доле клиентов.
49. [ ] **FR-49.** Система должна поддерживать canary rollout для подмножества клиентов.
50. [ ] **FR-50.** Система должна позволять задавать критерий отбора клиентов для canary rollout.
51. [ ] **FR-51.** Система должна позволять остановить rollout (stop): остановить дальнейшее распространение без изменения текущей глобальной версии конфигурации.
52. [ ] **FR-52.** Rollback rollout должен выполнять глобальный rollback конфигурации на baseline-версию rollout с созданием новой версии и переводом rollout в статус rolled_back.
53. [ ] **FR-53.** Система должна фиксировать параметры rollout в журнале аудита.

### 1.6. Audit Log

54. [ ] **FR-54.** Система должна сохранять факт создания конфигурации в журнале аудита.
55. [ ] **FR-55.** Система должна сохранять факт изменения конфигурации в журнале аудита.
56. [ ] **FR-56.** Система должна сохранять факт удаления конфигурации в журнале аудита.
57. [ ] **FR-57.** Система должна сохранять факт rollback в журнале аудита.
58. [ ] **FR-58.** Каждая запись аудита должна содержать идентификатор пользователя или сервиса-инициатора.
59. [ ] **FR-59.** Каждая запись аудита должна содержать timestamp.
60. [ ] **FR-60.** Каждая запись аудита должна содержать source IP или иной источник запроса.
61. [ ] **FR-61.** Каждая запись аудита должна содержать тип выполненной операции.
62. [ ] **FR-62.** Для операции изменения конфигурации запись аудита должна содержать diff.
63. [ ] **FR-63.** Система должна позволять искать записи аудита по сервису.
64. [ ] **FR-64.** Система должна позволять искать записи аудита по пользователю.
65. [ ] **FR-65.** Система должна позволять искать записи аудита по временному диапазону.

### 1.7. Клиентский агент / SDK

66. [ ] **FR-66.** Клиентский агент должен уметь устанавливать постоянное соединение с Centrifugo.
67. [ ] **FR-67.** Клиентский агент должен поддерживать автоматическое переподключение после потери соединения.
68. [ ] **FR-68.** Клиентский агент должен хранить локально последнюю успешно примененную версию конфигурации.
69. [ ] **FR-69.** Клиентский агент/SDK должен поддерживать применение конфигурации без перезапуска сервиса; интеграция применения в конкретный сервис выполняется на стороне клиента.
70. [ ] **FR-70.** Клиентский агент должен передавать серверу текущую примененную версию конфигурации при подключении или восстановлении соединения через механизм reconciliation, без передачи постоянного идентификатора агента.
71. [ ] **FR-71.** Клиентский агент должен уметь подтверждать успешное применение конфигурации.
72. [ ] **FR-72.** Клиентский агент должен отклонять применение некорректной/неприменимой конфигурации и отправлять на сервер дедуплицированную ошибку с ограничением частоты.
73. [ ] **FR-73.** Клиентский агент должен поддерживать восстановление пропущенных сообщений через механизм recovery, если он доступен для соответствующего канала Centrifugo. ([centrifugal.dev][2])
74. [ ] **FR-74.** Протокол reconciliation должен быть частью клиентского контракта: агент вызывает POST /v1/configs/{configId}/reconcile и передает текущую примененную версию; затем выполняет действие из ответа (none, recovery, snapshot); при snapshot выполняет GET /v1/configs/{configId} и применяет полученную актуальную версию.

## 2. Нефункциональные требования

### 2.1. Производительность и нагрузка

1. [ ] **NFR-1.** Система должна поддерживать не менее 50 000 клиентов.
2. [ ] **NFR-2.** Система должна поддерживать не менее 20 000 одновременных активных соединений.
3. [ ] **NFR-3.** Система должна поддерживать не менее 10 000 read-запросов в секунду на чтение конфигураций.
4. [ ] **NFR-4.** Система должна поддерживать не менее 1 000 write-запросов в секунду на изменение конфигураций.
5. [ ] **NFR-5.** Задержка публикации события доставки в Centrifugo после фиксации новой версии в PostgreSQL должна составлять не более 500 мс по p95.
6. [ ] **NFR-6.** Сквозная задержка доставки обновления конфигурации до подключенного клиента должна составлять не более 300 мс по p95.
7. [ ] **NFR-7.** Время ответа API на чтение конфигурации должно составлять не более 20 мс по p95 при номинальной нагрузке.

---

### 2.2. Масштабируемость

8. [ ] **NFR-8.** Система должна поддерживать горизонтальное масштабирование Config API Service.
9. [ ] **NFR-9.** Система должна поддерживать горизонтальное масштабирование компонента публикации событий доставки.
10. [ ] **NFR-10.** Система должна поддерживать горизонтальное масштабирование PostgreSQL read-path или чтения через реплики/кеширующий слой.
11. [ ] **NFR-11.** Система должна поддерживать sharding конфигураций.
12. [ ] **NFR-12.** Шардирование должно поддерживаться как минимум по namespace или service_id.
13. [ ] **NFR-13.** Конфигурация каналов Centrifugo должна поддерживать масштабирование по количеству подписок и публикаций. ([centrifugal.dev][4])

---

### 2.3. Отказоустойчивость

14. [ ] **NFR-14.** В системе не должно быть single point of failure.
15. [ ] **NFR-15.** Система должна продолжать работу при отказе одной ноды кластера приложений.
16. [ ] **NFR-16.** Система должна поддерживать автоматическое восстановление после отказа ноды.
17. [ ] **NFR-17.** Система должна корректно обрабатывать partial failure.
18. [ ] **NFR-18.** Целевая доступность системы должна составлять не менее 99.9%.

---

### 2.4. Консистентность

19. [ ] **NFR-19.** Операции записи конфигурации должны выполняться со strong consistency на уровне primary datastore.
20. [ ] **NFR-20.** PostgreSQL должна являться source of truth для актуального состояния конфигурации.
21. [ ] **NFR-21.** Доставка конфигурации клиентам может выполняться с eventual consistency.
22. [ ] **NFR-22.** Система должна гарантировать сходимость клиентов к актуальной версии конфигурации после восстановления связи.

---

### 2.5. Безопасность

23. [ ] **NFR-23.** Все внешние соединения должны использовать TLS.
24. [ ] **NFR-24.** Все межсервисные соединения должны использовать mTLS.
25. [ ] **NFR-25.** Все данные секретов должны быть зашифрованы at rest.
26. [ ] **NFR-26.** Система должна поддерживать RBAC или ACL для доступа к конфигурациям.
27. [ ] **NFR-27.** Система должна запрещать клиенту доступ к конфигурациям, не относящимся к его области видимости.

---

### 2.6. Наблюдаемость

28. [ ] **NFR-28.** Система должна собирать метрику latency публикации события доставки.
29. [ ] **NFR-29.** Система должна собирать метрику сквозной latency доставки конфигурации клиенту.
30. [ ] **NFR-30.** Система должна собирать метрику delivery lag.
31. [ ] **NFR-31.** Система должна собирать метрику количества активных соединений.
32. [ ] **NFR-32.** Система должна собирать метрику количества успешных и неуспешных доставок.
33. [ ] **NFR-33.** Система должна вести структурированные логи.
34. [ ] **NFR-34.** Система должна поддерживать correlation_id для трассировки операций.
35. [ ] **NFR-35.** Система должна поддерживать distributed tracing.
36. [ ] **NFR-36.** Система должна применять rate limiting на уровне API Gateway / Ingress по принципу token bucket как минимум в разрезах per service account и per user, с отдельными лимитами для write-операций.
37. [ ] **NFR-37.** Система должна предоставлять технические endpoints /health и /ready для мониторинга и оркестрации.
38. [ ] **NFR-38.** При превышении лимита система должна возвращать HTTP 429 с Retry-After; доля запросов, ограниченных rate limiting, должна собираться отдельной метрикой.
39. [ ] **NFR-39.** Конфигурация rate limiting должна поддерживать параметры rate и burst и обновляться без перезапуска API Gateway / Ingress.

## 3. Архитектурные требования

### 3.1. Общая архитектура

1. [ ] **AR-1.** Система должна включать отдельный компонент Config API Service.
2. [ ] **AR-2.** Система должна использовать PostgreSQL как основной слой хранения конфигураций и версий.
3. [ ] **AR-3.** Система должна включать отдельный компонент асинхронной публикации событий доставки после фиксации изменений в PostgreSQL.
4. [ ] **AR-4.** Система должна использовать Centrifugo как компонент доставки обновлений клиентам.
5. [ ] **AR-5.** Система должна включать клиентский компонент в виде SDK, sidecar или отдельного agent-процесса.

---

### 3.2. Распределённость

6. [ ] **AR-6.** Кластер PostgreSQL должен состоять минимум из 3 узлов с учетом primary и реплик.
7. [ ] **AR-7.** Архитектура PostgreSQL-кластера должна поддерживать автоматическое переключение primary при отказе.
8. [ ] **AR-8.** Система должна поддерживать репликацию данных между узлами PostgreSQL.
9. [ ] **AR-9.** Репликация данных должна обеспечивать сохранность конфигураций при потере одной ноды.
10. [ ] **AR-10.** Система должна корректно обрабатывать временную недоступность отдельных узлов.

---

### 3.3. Событийная модель

11. [ ] **AR-11.** Каждое изменение конфигурации должно порождать отдельное событие доставки.
12. [ ] **AR-12.** Событие доставки должно содержать идентификатор конфигурации.
13. [ ] **AR-13.** Событие доставки должно содержать номер новой версии.
14. [ ] **AR-14.** Событие доставки должно содержать timestamp.
15. [ ] **AR-15.** Событие доставки должно публиковаться асинхронно после успешной фиксации транзакции в PostgreSQL.
16. [ ] **AR-16.** Centrifugo должен использоваться как канал распространения событий доставки до клиентов через подписки на каналы. ([centrifugal.dev][1])

---

### 3.4. Обработка отказов

17. [ ] **AR-17.** Система должна поддерживать retry-механизм для временно недоступных компонентов.
18. [ ] **AR-18.** Retry-механизм должен использовать exponential backoff с full jitter.
19. [ ] **AR-19.** Операции публикации события доставки должны быть идемпотентными.
20. [ ] **AR-20.** При расхождении версий клиента и сервера должна выполняться version reconciliation.
21. [ ] **AR-21.** При отставании клиента система должна поддерживать сценарий snapshot + catch-up через явный reconcile-протокол (POST /reconcile -> action), с обязательным fallback на snapshot при недоступности recovery.
25. [ ] **AR-25.** Для операций публикации события доставки должны быть заданы параметры retry: base delay = 100ms, max delay = 30s, max attempts = 8.
26. [ ] **AR-26.** Формат каналов доставки должен быть стабильным и включать service и environment (например, service:{service_key}:{environment}).
27. [ ] **AR-27.** Если recovery завершился ошибкой (например, окно истории истекло или позиция недоступна), агент должен автоматически перейти на сценарий snapshot без ручного вмешательства.
28. [ ] **AR-28.** Endpoint POST /v1/rollouts/{rolloutId}/rollback должен определять baseline-версию rollout и выполнять эквивалент глобального rollback конфигурации с публикацией новой версии всем целевым клиентам.
29. [ ] **AR-29.** Механизм rate limiting должен обеспечивать консистентное применение лимитов при горизонтальном масштабировании API Gateway / Ingress.
30. [ ] **AR-30.** Операция публикации переводится в dead-состояние при исчерпании max attempts либо при неретраебельной ошибке (например, ошибка валидации payload, 4xx, кроме 429).
31. [ ] **AR-31.** Для dead-событий система должна поддерживать re-drive: ручной запуск повторной обработки и плановый фоновый re-drive с ограничением числа повторных циклов.
32. [ ] **AR-32.** Система должна собирать метрики retry/dead (attempt_count, доля dead, время до успешной публикации) и генерировать алерт при превышении порога dead.
33. [ ] **AR-33.** Retry должен применяться только к временным ошибкам (network timeout, 5xx, 429); для неретраебельных ошибок повтор не выполняется.

---

### 3.5. Работа с медленными клиентами

22. [ ] **AR-22.** Система должна уметь определять медленного клиента по факту отставания его версии от актуальной.
23. [ ] **AR-23.** Система должна поддерживать повторную синхронизацию медленного клиента через получение актуального snapshot из основного хранилища.
24. [ ] **AR-24.** Медленный клиент не должен блокировать доставку обновлений другим клиентам.

## 4. Требования к тестированию

1. [ ] **TR-1.** Для бизнес-логики системы должны быть реализованы unit-тесты.
2. [ ] **TR-2.** Для межкомпонентного взаимодействия должны быть реализованы integration-тесты.
3. [ ] **TR-3.** Для системы должно быть проведено нагрузочное тестирование доставки конфигураций.
4. [ ] **TR-4.** Нагрузочное тестирование должно включать эмуляцию не менее 10 000 клиентов для MVP.
5. [ ] **TR-5.** Расширенный сценарий нагрузочного тестирования должен предусматривать эмуляцию до 50 000 клиентов.
6. [ ] **TR-6.** Нагрузочное тестирование должно включать массовое обновление конфигураций.
7. [ ] **TR-7.** Должно быть проведено тестирование отказа одной ноды приложения или узла хранения.
8. [ ] **TR-8.** Должно быть проведено тестирование сетевых задержек.
9. [ ] **TR-9.** Должно быть проведено тестирование восстановления клиента после разрыва соединения.
10. [ ] **TR-10.** Должно быть проведено тестирование восстановления доставки через history/recovery механизм Centrifugo в пределах заданного окна хранения. ([centrifugal.dev][2])
11. [ ] **TR-11.** Нагрузочное тестирование должно включать сценарий злоупотребления write-запросами (например, 10 000 RPS от одного клиента) с проверкой ответов HTTP 429 и сохранения SLA для остальных клиентов.

---

## 5. Требования к MVP

1. [ ] **MVP-1.** MVP должен включать кластер хранения минимум из 3 узлов.
2. [ ] **MVP-2.** MVP должен поддерживать не менее 10 000 эмулируемых клиентов.
3. [ ] **MVP-3.** MVP должен обеспечивать публикацию события доставки после записи новой версии конфигурации в PostgreSQL менее чем за 200 мс по p95.
4. [ ] **MVP-4.** MVP должен демонстрировать hot update конфигурации без перезапуска сервиса.
5. [ ] **MVP-5.** MVP должен демонстрировать rollback конфигурации.
6. [ ] **MVP-6.** MVP должен демонстрировать сохранение работоспособности после отказа одной ноды приложения или узла хранения.
